## 5. 实测方差分析、D1 阈值模拟与新发现的 `stats.py` 下界问题

### 5.1 实测检查点方差特征

汇总 3 条轨迹全部 42 个检查点层（其中 36 个内部检查点满足 $0 < \hat{\mu}_k < 1$）：
- 连续评分 $y \in [0, 1]$ 的样本方差与同均值二项分布方差 $\hat{\mu}_k(1-\hat{\mu}_k)$ 之比：
  - **均值**：`0.5570`
  - **中位数**：`0.5128`
- 即 OfficeVal 连续完成度评分的真实条件方差约为二元成败（Bernoulli）方差的 **51%–56%**。

### 5.2 关键代码发现：`stats.py` 中 `lower_drop` 的无条件 `newcombe_lb` 截断

在核对为什么 `060.r03` 在 `[28, 32]` 上（$\hat{V}_2(c_{28}) = 0.375 \to \hat{V}_2(c_{32}) = 0.0$，且 `s2[32]` 的 8 条分支全部为 0）仍被判为 `diffuse_loss` 时，定位到 [`stats.py`](../src/l2_sandbox/stats.py) 第 113–119 行的实现与设计页第 3 节存在一处关键偏差：
- **设计页第 3 节规定**：「`lower` / `upper` 是单侧置信界：布尔终点用 Newcombe 区间，有界得分用 bootstrap；端点是终态时按单样本处理。」
- **`upper()`（第 57 行）的实现**：仅在样本方差为 0（`max(vals) == min(vals)`）时才用 `wilson_hi` 兜底。
- **`lower_drop()`（第 89、119 行）的实现**：对**所有**有界连续得分无条件执行了 `return min(diffs[idx], newcombe_lb)`！
  - 因为 `newcombe_lb` 把连续得分当作方差最大的二元 `{0, 1}` 样本处理，只要连续得分的真实方差小于二元方差（实测中位数仅为二元方差的 51%），`newcombe_lb` 就几乎恒小于 bootstrap 下界 `diffs[idx]`，导致 `min(diffs[idx], newcombe_lb)` **实质上屏蔽了连续得分的 bootstrap 下界，强制退化为最保守的二元 Newcombe 下界**。
  - **实测影响**：在 `060.r03` 的 `[28, 32]` 区间上，纯 bootstrap 单侧下界为 **`0.1250`**（高于区间阈值 `0.1143`，可检出 `concentrated_interval`），但被 `min(..., newcombe_lb)` 压低到了 **`0.0197`**，从而漏检为 `diffuse_loss`。

## 6. 结论与决策建议

1. **关于 D1（判定阈值）**：
   - 建议**改回设计（`design_v0_point`）**：在实测方差比（`0.557`）下，`design_v0_point` 的零假设总误报率仅为 `1.0%–1.65%`（远低于 $\alpha = 5\%$），同时在所有下跌幅度与样本量下均比 `code_v0_upper` 提升 **+2% 至 +13%** 的检出功效。
   - 同时建议将 `stats.py` 中 `lower_drop` 的 `min(diffs[idx], newcombe_lb)` 修正为与 `upper()` 对称：**仅在两侧样本方差均为 0（或对应侧方差为 0）时用 Wilson/Newcombe 兜底**，恢复有界连续得分的 bootstrap 置信下界（由于 F1 已将付费分支与统计代码解耦，修正后可直接对本批 228 条已跑分支做零成本 `cache_only` 重算）。
2. **关于正式 $N_1 / N_2$**：
   - $N_1=4, N_2=8$ 仅对 $\Delta \ge 0.70$ 有把握，且在 $p_0 \approx 0.43$（如 `004.r00`）时 $N_1=4$ 容易因网格随机波动选偏区间。
   - 正式 M3 建议采用 **`N1=8, N2=16, stride=4`**（对 $\Delta = 0.55$ 集中检出率达 `93%–95%`、单步精确检出率 `72%–73%`，成本比 `12/24` 节省 33%）或设计默认值 **`N1=12, N2=24, stride=4`**（对 $\Delta = 0.45$ 集中检出率仍达 `93%`）。
3. **关于 DeepSeek 35 请求预算与收尾瓶颈**：
   - F20 数据清楚表明：3 条失败父轨迹及其在 $k \ge 28$ 的续跑分支 **100% 死于 `request_budget`**（模型在剩余 3–7 步时仍在做 LibreOffice 渲染预览或微调，未能及时写入 `/workspace/submission/`）。这直接支撑了 L3 预算配速／收尾瓶颈假说的检验价值。
