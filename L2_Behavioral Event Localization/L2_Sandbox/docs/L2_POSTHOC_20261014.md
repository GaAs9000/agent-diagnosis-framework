# L2 行为诊断续分析：2026-10-14

继续读取 M1 的实际轨迹后，已有三项具体诊断：Sokoban 的搜索状态转移错误可在同一原生棋盘上复现；Word 与 Excel 的父轨迹均没有将检查过程转换为持久交付；Word 的恢复分支还包含独立的文档质量失败。

新增实验 API 调用为 0。除了读取现有证据，只执行了隔离的本地原生引擎机制对照。原 81 份执行包身份、冻结源码、曲线及其事实/结果/预测绑定均已复核；主实验 HTTP 准入仍为 1,280。

## 1. Sokoban：搜索器把推箱后的玩家位置算错

父轨迹第 14 回合（原始请求 `r000013`）生成的搜索器，在推箱之后使用：

```python
new_p_pos = p
```

这保留了推箱前的玩家位置。原生规则要求玩家进入箱子原来的格子，应为：

```python
new_p_pos = box_pos
```

原生第一处推箱中，玩家从 `(4,1)` 移到原箱子位置 `(3,1)`；错误搜索器仍按 `(4,1)` 规划后续可达路径。由此生成的 40 步路径被它自己判为可解，原生游戏却没有解开第一关。

该回合首先触发单次最多 30 步的限制，没有留下接受历史。第 15 回合分成 25+15 步执行后，一只箱子进入非目标角落 `(1,1)`。后续多次重置并重跑错误路径，父轨迹最终没有解开第一关。

本地受控对照提取原始纯搜索函数，在相同初始棋盘上只改这一行：原函数重现 40 步路径，原生 `levels_solved=0`；修改后生成 33 步路径，原生 `levels_solved=1` 并进入第二关。没有执行原始整条带 subprocess/日志写入的命令，没有访问评分器或为 Agent 注入答案。原始与兼容镜像的公开引擎及 levels 模块由根代理独立读取，字节一致。

因此，**这段生成程序的状态建模错误及局部修复效果已得到验证**。这项确定性程序对照不等于对 Agent 后续成功概率的随机干预，也没有测量官方全任务分数的变化。

同检查点的轨迹补充了行为线索：在 `k=14/15/16`，成功与失败分支的首个续跑回合都保留错误赋值；成功分支后来分别在第 18、17、18 回合改为 `box_pos`，失败配对保持错误搜索器。相同检查点控制了剩余请求预算，但“后期修复与成功同现”仍是事后关联，不能把后来修复冒充首轮谓词 `P(j)`。

第 14 回合错误赋值的窄语法谓词在父轨迹成立，但现有 `c13` 第二阶段两条分支都没有这一赋值，`P` 组 0 条、非 `P` 组 2 条。按每组至少 4 条的合同，只能记 `untestable`。

证据：`posthoc/20261014/sokoban.json`、`mechanism_sokoban/summary.json`。公开模块与私有评分器模块的来源及 SHA 分开记录；私有评分结果仅用于本次事后核对，不进入未来 Agent 提示。

## 2. Excel：一直计算和检查，没有保存；保存之后仍有计算质量问题

父轨迹 35 次请求、35 次工具调用持续读取工作簿、抽取数值、检查公式和比较重量。所有持久工作区差分为空，没有保存文件，也没有把文件放错目录的证据。第 24–28 回合仍在检查和打印；第 24 回合甚至包含只有 `pass` 的循环。

第二阶段在同一检查点的结果为：

| 检查点 | 相同剩余模型请求数 | 两条分支的官方得分 |
| --- | --- | --- |
| c24 | 11 | 未交付 / 10分（满分25） |
| c25 | 10 | 未交付 / 10分（满分25） |
| c26 | 9 | 10分（满分25） / 未交付 |
| c27 | 8 | 两条均未交付 |
| c28 | 7 | 两条均未交付 |

这批第二阶段工具执行均无退出错误。非零分支后来填入并保存 F/G 列，零分分支继续检查，没有文件修改。配对控制了预算，表明同样剩余预算下可以出现不同的交付行为；跨检查点的下降还同时包含剩余预算缩短，不能单独归因于某个检查动作。

第一个重采样回合全部仍是检查或计算；保存分歧发生在以后。例如 c26 的非零分支在第 29 回合保存，同点失败分支用尽 9 个剩余请求仍未保存。不能用最终“保存了”或“得分了”定义首轮 `P(j)`。

部分分数也揭示内容质量问题：宽范围 `range(6,15)` 会把已有合计行再次加入；“标签附近最近数值”会把 Sheet2 的单项重量 `2.695` 当总量，而真正总量 `17.422` 位于更远位置。保存件仍有 H 列公式和结构定位规则未满足。因此，“先产生交付”与“正确抽取/计算”需要分别检验。

证据：`posthoc/20261014/excel.json`，含每个请求、状态差分、保存动作、实际保存单元格和已有官方结果。

## 3. Word：交付缺失与结构质量失败必须分开

父轨迹 35 个请求全部检查原输入，初末工作区内容相同；没有中间文档、脚本或放错目录的输出。

c8 的四条续跑有同样原生首请求、同样输入状态和 27 个剩余请求。第一个续跑回合（第 9 回合）全部继续只读检查，后续结果却不同：

| 分支 | 实际结果 |
| --- | --- |
| k008-s1-i01 | 第 33 回合交付，官方 9/15 |
| k008-s2-i01 | 第 29 回合交付有效 DOCX，官方 0/15 |
| k008-s1-i00、k008-s2-i00 | 始终未交付 |

两份交付 DOCX 都完整可读，没有二进制损坏证据。9 分分支重建扁平表格，满足去空行和行间距规则，但丢失指定文本并未满足全部横线要求；0 分交付分支修改外层表格，嵌套表格仍保留 29 个空行，三项正向格式规则均未通过。

实现和质量选择发生在第 29、32–33 回合，远晚于 c8 的第一次续跑动作。这不能证明第 8–12 回合是关键原因，也不能把所有零分解释成未交付。第 8 回合的第一阶段高分样本没有在第二阶段得到非零复现，应保留为不稳定线索。

证据：`posthoc/20261014/word.json`，含封签、首请求、完整动作时间线及保存文档 XML。

## 4. 对当前 L2 方法的影响

原始三个任务的 `rules@1` 为什么假说数量均为 0，因为 `diffuse_loss` 没有触发第二次假说提出。当前报告中的解释均来自本次事后分析，不能补记成原始规则分析器已经预测正确。

规则价值预测把首次工具错误之后的检查点直接预测为失败终点值。实际首次错误分别在 Word 第 6 回合、Excel 第 7 回合、Sokoban 第 1 回合，包含可恢复的 API 用法、路径或执行权限错误。此后的部分检查点仍有非零或通过样本，特别是 Sokoban。外层 Python 的退出码 0 也不能证明它生成的搜索模型或内部原生动作在语义上正确。

`p0=0.5` 占位下，规则相对线性基线的技能分为 Word `+0.515`、Excel `-0.563`、Sokoban `-0.621`。这些数值没有已测基线支撑。本次仅做占位参数敏感性重算：Excel 在假定 `p0=1.0` 时可变为微弱正值；Sokoban 在所有测试的正 `p0` 上均为负。原预测与评分未修改，不能据这些探索数值排名分析器。

继续开发应分别表达可恢复的工具错误、持续无持久进展、错误的任务状态模型、修复事件，以及交付件的结构/数值不变量。尤其需要严格绑定谓词时间：**先发生的动作才可作为该回合的解释特征；后来的修复、最终交付和得分不能倒灌到先前谓词。**

独立审阅核对了 Word 时间线、Excel 同点分支、187 条 Sokoban 工具 stdout 和本地探针来源/单行差异，没有发现实质性不一致。当前可交付的是行为事实、候选解释和一个已验证的局部程序机制；自动定位与事前解释预测的有效性仍需要新证据。
